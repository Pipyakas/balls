Balls / a guide through the code

How the code is built, how it is laid out, how the engine-agnostic core is designed and how its pieces link together, and how each front end (SDL3, the web build, Unreal, Unity) sits on top of it. Read it top to bottom: every chapter uses only what the ones before it introduced. The game design document specifies behaviour; this page describes the code, and the knowledge report collects what is worth knowing about it. Checked against main at 2026-11-02 (3aba6b1); file paths are relative to the repository root.

The #### blocks are real code, each captioned with its file and line range. Lines cut for length are marked // ..., and a few grey comments are notes added for this guide. Each block says what the code is for, then walks through how it works and why it was written that way.

Overview

The game is one C++20 library, balls_core, that holds every rule: levels, launchers, spawning, the simulation, the editor model, the menus' content and order, settings, the benchmark and the automation API. It has no window, no renderer and no engine types. Physics, the one part that has to be fast on very different hardware, lives in separate plugins the core loads at run time. A front end is the rest: a window or an engine, input, drawing, and a thin layer that turns the core's models into widgets.

Three rules hold the structure together, and every chapter below is an application of one of them:

  1. Dependencies point down. A front end includes the core; the core never includes a front end; a physics plugin sees only sim/PhysicsBackend.h and the shared step math. A grep of source/core finds no SDL, Unreal or Unity header.
  2. Rules are written once. Anything two front ends would otherwise both implement (screen order, button labels, layout rectangles, the editor's tools, the control API, the toasts' wording) is a model in the core that each front end only draws.
  3. Hardware is chosen at run time. One build carries every backend; which ones run is decided on the player's machine, from what loads, what the player picked and what the benchmark measured. A missing driver turns into a reason string in a menu, never a crash.

Where builds run

The low-end laptop L2 (i7-7500U, 16 GB, Radeon R7 M445) is the target the game is tuned for, but it compiles on two cores. scripts/remote/BuildOnDesktop.py pushes the current commit to L2's bare clone, has the two-GPU desktop (16 threads) build it inside its balls-dev distrobox, rsyncs build/linux/bin to /mnt/data/balls/run on L2 and runs balls_tests there (--play also starts a level and prints the frame rate). One game, as objects

  • GameSession (game/GameSession.h) owns the level's rules by value: a Simulation, a LauncherQueue, a SpawnController, the LevelData and an AdditionGovernor that keeps ball additions from stalling a frame. It turns player actions (chooseLauncher, startAutoRelease, selectSpawnRate, selectBallLimit, requestBackend, restart) into spawns and state.
  • Simulation (sim/Simulation.h) owns the BrickBoard (hits left, dirty cells, animation), the TargetField (a per-colour BFS that tells a bouncing ball where the nearest matching brick is) and the backend through a BackendHandle.
  • BackendHandle is std::unique_ptr<PhysicsBackend, BackendRelease>; the deleter calls the plugin's own ballsDestroyBackend and holds a shared_ptr<DynamicLibrary>, so a plugin stays loaded while any object from it lives.
  • Levels are values. loadLevel/saveLevel, LevelRepository (folders), LevelImporter and LevelWatcher (hot reload, owned by ScreenFlow) are separate pieces around one plain LevelData.

Exception-free error propagation with Result<T>

The return type of core functions that can fail on bad input, such as level parsing and loading.

source/core/common/Result.h:12-31
template <typename T>
class [[nodiscard]] Result {
public:
    Result(T value) : storage(std::in_place_index<0>, std::move(value)) {}
    Result(Error error) : storage(std::in_place_index<1>, std::move(error)) {}

    bool hasValue() const { return storage.index() == 0; }
    explicit operator bool() const { return hasValue(); }

    T& value() { return std::get<0>(storage); }
    const T& value() const { return std::get<0>(storage); }
    T& operator*() { return value(); }
    const T& operator*() const { return value(); }
    T* operator->() { return &value(); }
    const T* operator->() const { return &value(); }
    const std::string& error() const { return std::get<1>(storage).message; }

private:
    std::variant<T, Error> storage;
};

The class wraps a std::variant<T, Error> to return either a valid result or a diagnostic message without dynamic memory allocations for successful paths. The [[nodiscard]] attribute prevents callers from accidentally ignoring failures, while pointer-style dereference operators (* and ->) allow idiomatic access. The error is a message meant for the player, so a front end can show a level's load error as text without knowing what went wrong.

Adaptive 60 FPS spawn budget throttling

Calculates how many balls may be added this frame so stepping plus adding stays inside a share of a 60 FPS frame.

source/core/game/AdditionGovernor.cpp:55-69
double AdditionGovernor::additionSeconds(BallCount liveBalls, bool freeFlight) const {
    const double frameBudgetSeconds = (freeFlight ? freeFlightBudgetShare : steppingBudgetShare) / targetFramesPerSecond;
    const double chargedOtherSeconds = std::min(otherSeconds, frameBudgetSeconds * largestOtherShare);
    return std::max(0.0, frameBudgetSeconds - chargedOtherSeconds - stepSecondsPerBall() * static_cast<double>(liveBalls));
}

BallCount AdditionGovernor::allowance(BallCount liveBalls, bool freeFlight) const {
    const double spare = additionSeconds(liveBalls, freeFlight);
    if (spare <= 0.0) {
        return 0;
    }
    const double balls = spare / (stepSecondsPerBall() + secondsPerAddedBall);
    const BallCount most = std::max(liveBalls, smallestScaledBalls);
    return balls >= static_cast<double>(most) ? most : static_cast<BallCount>(balls);
}

The method additionSeconds reserves frame time by subtracting non-physics overhead (front-end rendering and UI, charged at most half the budget) and projected stepping time from the frame budget. In allowance, remaining spare time is divided by the sum of per-ball step cost and per-ball addition cost to compute a safe addition limit. In free flight (when all bricks are destroyed), a higher budget fraction (0.85 instead of 0.50) is allocated.

One tick

The simulation advances in fixed 1/120 s ticks with at most four per frame, so a slow frame drops time instead of spiralling. All per-ball work is one virtual call.

source/core/sim/Simulation.cpp (condensed)
void Simulation::advance(float frameSeconds) {
    accumulator = std::min(accumulator + frameSeconds, tickSeconds * maxTicksPerFrame);
    const int ticks = int(accumulator / tickSeconds);
    accumulator -= ticks * tickSeconds;
    if (ticks > 0) tick(ticks);
}
void Simulation::tick(int substeps) {
    if (!pendingSpawns.empty()) { physics->addBalls(pendingSpawns); pendingSpawns.clear(); }
    syncBoardIfChanged();                          // uploads only the changed cells
    hits.clear();
    physics->step(stepParams(substeps), hits);     // the one call that does the per-ball work
    if (physics->resolvesHitsOnDevice()) applyDeviceHits();   // a GPU already counted the hits
    else                                  resolveHits();      // host applies hits to BrickBoard
}

Resolving brick hits and removing balls

Processes collision reports from physics backends, damages bricks, and removes balls in stable reverse order.

source/core/sim/Simulation.cpp:316-343 (condensed)
void Simulation::resolveHits() {
    killedBalls.clear();
    bool anyDestroyed = false;
    for (const BallHit& hit : hits) {
        const bool wasAlive = brickBoard.bricks()[hit.brick].isAlive();
        if (!wasAlive) {
            continue;
        }
        brickBoard.applyHit(hit.brick);
        anyDestroyed = anyDestroyed || !brickBoard.bricks()[hit.brick].isAlive();
        killedBalls.push_back(hit.ball);
        // ...
    }
    // Backends report hits in ball order, so this is usually a reversal rather than a sort.
    if (std::ranges::is_sorted(killedBalls)) {
        std::ranges::reverse(killedBalls);
    } else {
        std::ranges::sort(killedBalls, std::greater<>{});
    }
    physics->removeBalls(killedBalls);
    if (anyDestroyed) {
        brickBoard.settleColumns();
    }
}

Each reported BallHit is checked against BrickBoard::isAlive to ignore redundant hits from balls colliding with the same brick in one tick. The indices of the balls that hit are sorted in descending order (via std::ranges::reverse since physics backends yield hits in ascending index sequence) because PhysicsBackend::removeBalls takes descending indices: removing from the back never moves a ball whose index is still in the list. If any brick was destroyed, BrickBoard::settleColumns moves the bricks behind it into the gap (raiseFully).

Transactional stroke editing and undo bundling

Groups continuous pointer drag events into single undo operations while editing brick layouts.

    strokeErases = erase;

void EditorSession::strokeCell(int column, int row) {
    const BrickLayout& bricks = editor.level().bricks;
    if (!strokeActive || column < 0 || row < 0 || column >= bricks.width || row >= bricks.height) {
        return;
    }
    if (lastStrokeCell && lastStrokeCell->first == column && lastStrokeCell->second == row) {
        return;
    }
    applyBrickTool(column, row);
    // Extend picks the brick under the first cell of a stroke and grows it over the cells after that.
    strokeDragging = lastStrokeCell.has_value() || currentTool != EditorTool::Extend || selectedBrickId != emptyBrickId;
    lastStrokeCell = std::make_pair(column, row);
    edited();
}

When a pointer click starts a drawing action, beginStroke invokes LevelEditor::beginEdit to push a snapshot of LevelData onto the undo stack, ensuring a multi-cell drag creates only one undo entry. While dragging, strokeCell guards against duplicate edits when the cursor hovers on the same cell and delegates cell modifications to applyBrickTool. Calling endStroke on pointer release only clears the stroke flags; the undo entry was already pushed by beginEdit.

A backend is a C++ abstract class created and destroyed through C entry points. That split keeps the hot interface ergonomic (a virtual call per step) while symbol lookup stays name-stable across compilers. Library lifetime binding with BackendHandle

A BackendHandle owns a physics backend pointer along with a reference-counted handle to the dynamic library that implements it. This guarantees the underlying shared library remains loaded in process memory for the entire lifetime of the backend.

source/core/sim/BackendHandle.h:8-19

    DestroyBackendFunction destroy = nullptr;
    std::shared_ptr<DynamicLibrary> library;

    void operator()(PhysicsBackend* backend) const {
        if (backend && destroy) {
            destroy(backend);
        }
    }
};

using BackendHandle = std::unique_ptr<PhysicsBackend, BackendRelease>;

The custom deleter BackendRelease captures both the plugin's exported destroy function and an ownership reference in std::shared_ptr<DynamicLibrary>. When the std::unique_ptr alias BackendHandle falls out of scope, operator() executes destroy(backend) inside the plugin before the library reference count decrements. This prevents invalid memory accesses and crashes that occur when a shared library is unmapped while virtual dispatch tables or backend destructors are still active. It also ensures that backend memory is deallocated by the same C runtime allocator that allocated it.

Building and retiring off the frame

Loading a plugin, opening a GPU and compiling pipelines take long enough to drop frames, and so does freeing gigabytes of device memory. BackendWorker::shared() is one process-wide thread that does both: build(kind) returns a BackendBuild the session polls each frame, and retire(handle) destroys an old backend. The old backend keeps stepping until the new one is ready; then Simulation::replaceBackend moves the balls across in chunks of 220 (migrationChunkBalls) and hands the old handle to the worker.

Asynchronous backend compilation and retirement

Opening GPU contexts, compiling shader pipelines, and releasing gigabytes of VRAM cause noticeable frame drops. BackendWorker executes these heavy operations on a persistent dedicated background thread.

The worker thread manages an internal FIFO job queue guarded by a mutex and condition variable. Calling build enqueues a closure that executes createBackend off-thread and populates a BackendBuild token that the gameplay session polls each frame without blocking. If a user quickly switches choices again, BackendBuild::abandon marks the in-flight build so the resulting backend is retired immediately upon completion. Conversely, retire defers destroying old BackendHandle instances so expensive driver deallocations occur off the rendering and physics threads.

Chunked ball migration during backend replacement

When switching physics backends during active gameplay, Simulation::replaceBackend transfers existing balls from the retired backend into the newly initialized backend in manageable chunks.

source/core/sim/Simulation.cpp:73-104 (condensed)
BackendReplacement Simulation::replaceBackend(BackendHandle backend, size_t chunkBalls) {
    BackendReplacement replacement{std::move(physics), 0};
    physics = std::move(backend);
    // ... synchronizes board state and collision configuration
    syncBoardIfChanged();
    PhysicsBackend& previous = *replacement.retired;
    const size_t total = previous.ballCount();
    if (total > physics->ballCapacityLimit()) {
        replacement.ballsToRefill = total;
        return replacement;
    }
    while (previous.ballCount() > 0 && physics->faultMessage().empty()) {
        const std::vector<BallSpawn> chunk = previous.takeTail(std::min(previous.ballCount(), chunkBalls));
        if (chunk.empty()) {
            break;
        }
        try {
            physics->addBalls(chunk);
        } catch (const std::bad_alloc&) {
            break;
        }
    }
    replacement.ballsToRefill = total - std::min(physics->ballCount(), total);
    return replacement;
}

The simulation swaps physics with the incoming backend handle and synchronizes brick board revisions. Balls are extracted from the old backend using takeTail in batches of chunkBalls (migrationChunkBalls, 220 = 1,048,576) and transferred via addBalls, preventing transient memory spikes from copying all live balls at once. If device memory exhaustion causes addBalls to throw std::bad_alloc or the backend reports a fault through faultMessage, migration halts gracefully. Any balls that could not be transferred are tracked in ballsToRefill and respawned over subsequent frames by GameSession::refillBatch.

Each ball fits into two 32-bit words: position packs 16 bits for x and 16 bits for y scaled to 65,535, while state stores two 13-bit signed direction components, 3 bits of colour, and 2 bits tracking bounces. The function encodeAxis maps board extents to unsigned 16-bit integers, while encodeComponent and signedComponent quantize unit direction vectors into 13-bit two's complement integers. Because all balls share a global speed parameter, decode reconstitutes full floating-point velocities by multiplying the normalized direction components by speed without storing per-ball magnitudes. Positions use the full 16-bit range (positionScale = 65,535); directions use ±4,095 of the 13 bits (directionScale).

Warp-level brick hit reduction and leader atomic subtraction

Deduplicates simultaneous brick collisions across threads in a CUDA warp using shuffle intrinsics, issuing a single atomic subtraction with refunds for excess hits. Called from the CUDA step kernel when balls collide with bricks.

source/backends/cuda/BallKernels.cu:161-176
__device__ __forceinline__ bool consumeBrickHit(int* brickHitsLeft, int brick) {
    const unsigned int peers = __match_any_sync(__activemask(), brick);
    const int lane = static_cast<int>(threadIdx.x) & 31;
    const int leader = __ffs(peers) - 1;
    const int wanted = __popc(peers);
    int granted = 0;
    if (lane == leader) {
        const int previous = atomicSub(&brickHitsLeft[brick], wanted);
        granted = max(0, min(previous, wanted));
        if (granted < wanted) {
            atomicAdd(&brickHitsLeft[brick], wanted - granted);
        }
    }
    granted = __shfl_sync(peers, granted, leader);
    return __popc(peers & ((1u << lane) - 1u)) < granted;
}

When a launch wave reaches a row of bricks, hundreds of thousands of balls hit the same few in one tick; per-ball compare-and-swap (CAS) loops serialized into 150 ms steps. The function consumeBrickHit uses __match_any_sync across active threads in a warp to find all peer lanes colliding with the same brick index. The elected leader thread (found via __ffs) performs a single atomicSub for the aggregate count wanted, and if the brick had fewer hits left than requested, immediately refunds the excess via atomicAdd. The total granted hits are broadcast across the warp with __shfl_sync, and prefix-popcount logic grants hits in lane order without any serialized CAS loops. A build with BALLS_RANK_WITH_ATOMICS uses a plain per-lane subtract-and-refund instead.

__device__ __forceinline__ void bidForSlot(unsigned int packed, unsigned int index, const VisibilityGrid& grid) {
    const unsigned int priority = slotPriority(index, grid.frameSeed);
    if ((priority >> 1) & grid.bidderMask) {
        return;
    }
    const int slot = slotForPacked(packed, grid);
    if (priority > static_cast<unsigned int>(grid.slots[slot] >> 32)) {
        atomicMax(&grid.slots[slot], (static_cast<unsigned long long>(priority) << 32) | packed);
    }
}

To avoid reading back gigabytes of ball coordinates when rendering up to 100M balls, the simulation rasterizes balls into a fixed-resolution visibility grid on the GPU. The function slotForPacked calculates the grid slot corresponding to a ball's 14-bit packed x and y coordinates. In bidForSlot, balls first filter themselves against grid.bidderMask based on a per-frame hashed priority from slotPriority, discarding low-priority candidates. Winning candidates execute a 64-bit atomicMax on the destination slot, packing the 32-bit hash priority in the high bits and the render word in the low bits, so one compare picks both the winner and its render word, and the readback is the grid's size whatever the ball count.

Ball visibility grid bidding compute shader

Selects winning balls per screen grid cell when millions overlap and writes winner priorities atomically. Dispatched during the visibility compute pipeline before drawing balls.

source/frontends/sdl/shaders/BallVisibility.hlsl:55-68
[numthreads(256, 1, 1)]
void computeMain(uint3 thread : SV_DispatchThreadID) {
    if (thread.x >= itemCount) {
        return;
    }
    const uint priority = slotPriority(thread.x);
    if (((priority >> 1) & bidderMask) != 0u) {
        return;
    }
    const uint slot = slotForPacked(balls[thread.x]);
    if (priority > priorities[slot]) {
        InterlockedMax(priorities[slot], priority);
    }
}

Drawing millions of sub-pixel balls creates severe fragment overdraw and vertex bottlenecking. computeMain executes the bidding phase of visibility culling: each ball hashes an instance index into a pseudo-random priority via slotPriority, projects its packed integer coordinates into a screen tile with slotForPacked, and claims the tile using InterlockedMax. Subsequent resolve and compaction passes stream the surviving balls directly into an indirect draw buffer without any CPU readback.

Ball vertex shader word decoding

Expands packed 32-bit ball records into circumscribing triangles in board clip space. Executed per-vertex on the GPU during the ball rendering pass in MainVS.

source/frontends/unreal/Shaders/BallsDraw.usf:20-33
void MainVS(uint VertexId : SV_VertexID, uint InstanceId : SV_InstanceID,
            out float4 OutPosition : SV_POSITION, out float2 OutLocal : TEXCOORD0,
            out nointerpolation float3 OutColor : TEXCOORD1)
{
    const uint Packed = PackedBalls[InstanceId];
    const float2 Center = float2(Packed & 16383u, (Packed >> 14u) & 16383u) * UnpackScale;
    const float2 Local = QuadCorners[VertexId];
    OutPosition = mul(float4(Center + Local * Radius, 0.0, 1.0), BoardToClip);
    // 0xFFFFFFFF marks a visibility-grid slot no ball won; it must not decode into a ball in the corner.
    OutPosition = (VertexOnly > 0.5 || Packed == 0xFFFFFFFFu) ? float4(1.0e6, 1.0e6, 0.0, 1.0) : OutPosition;
    OutLocal = Local;
    OutColor = Palette[(Packed >> 28u) & 7u].rgb;
}

MainVS uses QuadCorners[3] to emit an equilateral circumscribing triangle (3 vertices instead of 4 or 6 for a quad), unpacking integer coordinates (bits 0-13 for X, 14-27 for Y) and the color palette index (bits 28-30) from a single 32-bit integer word. Invalid or empty slots marked with 0xFFFFFFFFu are discarded by placing their clip-space positions off-screen.

12 · Conventions and workflow

Code

  • Classes PascalCase; functions and variables camelCase; named constants instead of magic numbers; comments say why.
  • Errors: Result<T> in level I/O and the bench, bool + std::string& error elsewhere; nothing across the plugin or C ABI throws.
  • Every commit builds and passes balls_tests. Titles are type(scope): summary (feat, fix, perf, refactor, docs, test, build, chore), the body says why.

Branches and machines

  • One trunk, main. Work happens on short feature/, fix/, build/ branches merged with --no-ff; main is never force-pushed.
  • Unmerged lines kept for reference: feature/backend-zen4, -rocm, -vulkanmulti (now on main in another form), feature/web-wasm, -wgsl, webgpu-compute (the old web attempts, replaced by the web build above), unity, perf/physics-cuts.
  • The repository is a bare clone with one worktree per machine: wt-main on L1 (source only) and /mnt/data/balls/wt-main on L2. Builds run on the two-GPU desktop and are tested on L2 (chapter 1). CMake caches absolute paths, so a moved worktree needs its build/ deleted.

Publishing

  • scripts/submission/BuildSubmission.py regenerates submission from main: whitelist.txt picks the files, scrub.txt rewrites internal names. It is never edited by hand.
  • PublishSubmission.py <destination> re-attributes every commit to that destination's identity (targets.json), applies its own scrub file if it names one, and pushes.
  • GitHub (Pipyakas/balls, public) gets code only: MinimalGithub.py drops documentation, strips comments, writes a minimal README and force-pushes one parentless commit. The web build goes to its gh-pages branch.
